# Traffic Control и Jev для внешних ссылок

Продолжение существующей маршрутизации Spaces из `dev`. Настройки открываются
через меню Space → «Настройки маршрутизации».

## Порядок выбора Space

1. Первое совпавшее правило в списке. Правила можно перемещать стрелками.
2. Jev, если включён и подходящего правила нет.
3. Настроенный запасной Space при неоднозначном ответе, ошибке или таймауте.

У новых профилей запасной вариант — первый Space в текущем порядке. Можно
выбрать конкретный Space или последнее активное пространство. Существующий
выбор профиля сохраняется. Удалённый Space заменяется первым доступным.

Маска URL дополняет прежние условия «содержит», «совпадает» и RegEx. Например,
`github.com/Onigo/*` соответствует организации, а `*.example.com/*` — поддоменам.
Регистр домена не важен; регистр пути учитывается. Первое совпадение окончательно,
в том числе правило «последнее активное».

## Настройка Jev

Включить «Использовать Jev для внешних ссылок без подходящего правила», раскрыть
настройки, ввести API-ключ TypeSafe и нажать «Сохранить ключ». Кнопка проверки
подключения использует синтетический URL. Поле ввода очищается после сохранения;
сам ключ остаётся в профиле в зашифрованном виде через OSKeyStore.

Названия и идентификаторы текущих Spaces подставляются автоматически. Для каждого
можно описать его назначение; общий промпт также редактируется. Пример:

> Разработка, GitHub и техническая документация относятся к Work. Билеты и отели —
> к Travel. Покупки — к Shopping. Не угадывай содержание документов по их ID.

Порог по умолчанию — 70%, минимальный отрыв от второго варианта — 45 процентных
пунктов, ожидание ответа — 1000 мс. Вариант «недостаточно данных» участвует в
распределении вероятностей. Равенство лидеров всегда означает запасной вариант.
Эти числа — оценки модели, а не гарантия правильности классификации.

Поле «Проверить внешнюю ссылку» показывает итоговый Space, причину выбора и
вероятности без открытия вкладки. Проверка применяет тот же порядок правил,
Jev и запасного варианта, что и настоящее внешнее открытие.

## Границы поведения

- Jev работает только с внешними HTTP(S)-ссылками: системное открытие адреса,
  обычный запуск с URL и пакет внешних адресов. Cmd+T и ссылки внутри браузера
  не вызывают Jev. Прежняя ручная маршрутизация внутри браузера сохраняется.
- Приватные окна и режим без Spaces обходят Jev. IP-адреса, локальные имена,
  URL с логином/паролем и другие схемы не отправляются провайдеру.
- Передаются домен и путь, названия/описания Spaces и промпт. Query и fragment
  удаляются. История, содержимое страницы и cookies не передаются. Сам открываемый
  адрес остаётся неизменным. Путь тоже может содержать чувствительные сведения;
  это учитывается при включении функции.
- Используется `jev-1.14.0` и фиксированный endpoint TypeSafe System One.
  Нет повторных запросов или следования HTTP redirect провайдера. На весь запрос,
  включая расшифровку ключа и чтение ответа, действует общий таймаут.
- Решение принимается перед созданием вкладки и её первой загрузкой, чтобы сразу
  выбрать контейнер целевого Space. Поздний ответ не переносит уже открытую вкладку.
  Одновременно выполняются максимум четыре запроса; остальные идут в запасной Space.
- Изменение правил, настроек или состава Spaces во время запроса отменяет его
  применение. Внешнее открытие выполняется не более одного раза.

## Проверка

Автоматические проверки логики:

```sh
.zen-local/toolchains/node/bin/node --test tests/space-routing/*.test.mjs
```

Нативные browser tests зарегистрированы в
`src/zen/tests/space_routing/browser.toml`. Они включают реальные вкладки и
контейнеры, нативный обработчик пакета внешних адресов с обратным порядком ответов,
редактор и проверку без открытия вкладки. Запускать через подготовленную среду
`mach mochitest --flavor browser --headless zen/tests/space_routing`.

## Приёмка 23 октября 2026 года

Проверен изолированный кандидат
`b3f051c2f000068e55043a070066651d0bd82a2c` на macOS ARM64, Firefox 157.0.1.
Он включает изменения MCP до `aaf4a0fd`. Выполнены полный CLI build,
standalone package и запуск с отдельным чистым профилем Playground. Пакет
подписан ad hoc; полная подпись проверена после запуска. Использовались Node
22.23.3, Python 3.11.15, Rust 1.95.0, clang 22.1.8 и SDK macOS 26.5.

- 30 Node tests: без ошибок. Регрессия раннего `unload` при холодном запуске
  воспроизводилась до исправления и проходит после него.
- Все 11 файлов browser tests прошли: 23 274 успешных проверки, два ожидаемых
  TODO в прежних тестах, неожиданных результатов нет. TODO относятся к проверке
  доступности скрытой кнопки удаления и изменению `zen.workspaces.active`.
- Через настоящий интерфейс проверены ключ, промпт, описания Spaces, ручная
  маска, изменение порядка правил и выбор конкретного запасного Space.
  Шесть запросов предпросмотра дали ожидаемые решения за 187–261 мс и не
  создали вкладок; непрозрачные ссылки ушли в первый Space.
- Четыре системных URL-события, адресованных только PID Playground, создали
  ровно четыре вкладки: GitHub → Work, Booking → Travel, непрозрачный документ
  → Common, ручная маска → Travel. Контейнер Work присутствовал уже при
  создании вкладки и в первом сетевом запросе. Исходные query и fragment
  GitHub сохранились. Ответы Jev в этой проверке заняли 173–215 мс.
- При холодном запуске с двумя URL каждый открылся ровно один раз: GitHub
  в Work с его контейнером, Booking в Travel. Три ранее сохранённые непустые
  вкладки, Spaces, правила, запасной Space, промпт, описания и зашифрованный
  ключ пережили перезапуск. MCP переподключился с новой идентичностью;
  повторены чтение страницы, действие по свежему snapshot и навигация.

В Playground оставлен лимит ожидания 3000 мс. При проверке с 1000 мс на
холодном запуске обе ссылки открывались в запасном Space; причина решения
тогда отдельно не записывалась. Увеличенный лимит ограничивает максимально
возможное ожидание, а быстрые ответы применяются сразу. Значение по умолчанию
в новом профиле остаётся 1000 мс.

Найденная при проверке потеря первого URL исправлена: замена раннего пустого
chrome-документа Firefox больше не считается закрытием окна. Маршрутизатор
ожидает готовности `browser.xhtml` перед нативным открытием.

Машинные доказательства находятся в игнорируемом `.zen-local/traffic-control/`:
`browser-tests-summary.json`, `browser-previews.json`, `external-links.json`,
